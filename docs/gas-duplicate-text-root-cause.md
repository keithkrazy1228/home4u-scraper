## 1. バグ1:テキスト二重表示 — 原因

### 決定的な観測事実(生成物と全書き込み関数の突き合わせ)

| 項目 | 書き込み工程 | 状態 |
|---|---|---|
| 物件名・住所・調査期間(表紙) | BASE(a2gTplFillCoverV7_) | 正常 |
| 調査開始日・完了日・調査技師名 | BASE(a2gTplFillSurveyOverviewV3_/V7_) | 正常 |
| フッターページ番号 | **FINALIZE**(a2gTplUpdatePageNumbersV3_ 自動生成報告書.gs:2467-2481) | **二重** |
| サマリー結論文 | **FINALIZE**(a2gApplySummaryV86_ 報告書文章レイアウト_V86恒久.gs:38-62) | **二重** |
| 「今回の結論」見出し | **FINALIZE**(a2gApplyLimitedRestoreV88_ 報告書限定復元_V88.gs:64) | **二重** |
| 依頼主名「テスト様」 | **FINALIZE**(V88:72 ※「テスト様」形式はV88の整形。BASEは「テスト 様」形式) | **二重** |
| 調査対象キャプション | **FINALIZE**(V88:73) | **二重** |
| 責任者3名(冨田/山下隼也/小俣辰也) | **FINALIZE**(V88:75-78) | **二重** |
| 検収印スタンプ(冨田/山下/小俣) | **FINALIZE**(V88:80-83 insertShape) | **2セット** |
| 最終ページA2G印 | **FINALIZE**(V86:84-107 / V88:13-27) | **2個** |

→ **二重化した項目は「FINALIZE工程が書く項目」と完全一致。他工程の項目は1つも二重化していない。**
つまり原因は「FINALIZE工程の効果が同一デッキに2回載った」こと。

### なぜ2回載るのか

書き込み自体は全て `setText`(置換・冪等)で、1回の正常なFINALIZEでは二重化しない。
二重化には「**2つの実行が互いの結果を知らずに同じデッキへ書き込む**」ことが必要で、
その条件はこの設計に揃っている:

1. FINALIZEは写真の再取得(UrlFetchApp、1枚につき最大3リトライ:v81.gs:52-60、
   さらにV94の全写真再クロップ 報告書品質_V94恒久.gs:195-243 で全画像を再ダウンロード)を含む
   **最重量工程**で、GASの実行時間上限(約6分)でハードキルされやすい。
2. キルされた実行の編集は途中までコミット済み・進捗は未更新 → 次のトリガーが**同じFINALIZEを再実行**。
3. Slidesは共同編集マージ(OT)で編集を統合するため、**古いスナップショットに基づく
   setText/insertShapeが後から合流すると「置換」ではなく「追加」として合成され、
   同一テキストボックス内の文字列連結(例: `1 / 19`+`1 / 19`)やスタンプ2セットになる**。
   - スタンプは毎回「旧スタンプ削除→挿入」(V88:6-11)だが、相手の挿入が見えていない
     スナップショット上では削除対象が無く、結果2セット残る。観測と一致。
4. ロック(LockService)はトリガー経路には効いているが、上記2の「キル→再実行」は
   ロックでは防げない(死んだ実行はロックを手放すため)。
   加えて `activateA2GReportV102Production`(報告書追加写真_V96恒久.gs:455)が入れた
   毎分トリガー `processPendingA2GReportsV99` と、`a2gInstallV116Trigger`(V116:70-77)の
   毎分トリガー `processPendingA2GReportsV116` は**互いを削除しない**ため、
   両方が登録されたままだと毎分2本のトリガーが同時起動する
   (要確認: GASエディタ左の時計アイコン「トリガー」一覧のスクショで確定できる)。

### 過去に同じ症状と戦った形跡(コード内に現存)

- 小松ビル責任者名重複修正_V91.gs: `名前名前→名前` の正規表現置換で事後修理
- 報告書限定復元_V88.gs 内「V92: 責任者名が同一枠内で連結された場合も1回表示へ正規化」
  +「同位置・同文のシェイプ重複削除」
- 無題 4.gs: スライド2の重複シェイプ削除スクリプト
→ 対症療法が積み重なっており、根本(FINALIZE多重適用)は未対処。
  もみ消しはFINALIZE内にあるため、**もみ消し自体も多重実行の競合に巻き込まれ効かないことがある**。

## 2. バグ3:ページ数不一致(18枚/「19」表記/欠番18)— 原因確定

順序バグ。決定的で再現性100%:

1. FINALIZE原本がページ番号を刷る: `a2gTplUpdatePageNumbersV3_(presentation)`
   (自動生成報告書_v81.gs:377 で呼び出し、実装は自動生成報告書.gs:2467-2481。
   この時点の枚数19で「n / 19」を全ページに書く)
2. **その後**に V114ラッパーの `a2gNormalizeOpinionPagesV114_`
   (V114_全写真カード総合所見恒久修正.gs)が総合所見2ページを1ページに統合し、
   2ページ目を `pages[i].slide.remove()` で**削除**する。
3. ページ番号はその後刷り直されない → 実枚数18、フッターは「…17/19、(18欠番)、19/19」。

生成デッキの実測(総合所見=17/19、最終ページ=19/19、18欠番)と完全一致。

## 3. バグ2:「撮影場所:あなた」→「あな」見切れ — 原因(データ起因が濃厚)

- キャプションは診断結果シートの列 `散水場所説明1〜15` を写真ごとに1対1で表示する
  (報告書拡張_V92恒久.gs:40、報告書品質_V95恒久.gs:34・60、報告書追加写真_V96恒久.gs:12、
  表示は同:510 `label += '\n撮影場所:' + desc;`)。
- **コード全体に文字数切り詰め(slice/substring)は存在しない。**
- 写真1枚目=「あなた」、2枚目以降=「あな」は、`散水場所説明1=あなた`、
  `散水場所説明2〜4=あな` と**入力データ自体が異なる**可能性が濃厚。
- 確認方法: DBスプレッドシートの `04_診断結果管理` で案件 `fc74628b` の行の
  `散水場所説明1〜4` 列を見る(1分で確定できる)。

## 4. 修正方針の提案(最小修正・既存機能に触らない)

合意をもらえたら着手する。優先順:

1. **バグ3(確実・小)**: ページ番号刷り込みをパイプラインの真の最後へ移動。
   具体的には最終ラッパー(現状はV114の2つ目)の後、またはPDF工程冒頭で
   `a2gTplUpdatePageNumbersV3_` をもう一度呼ぶ1行追加+
   正規表現を二重化耐性に強化(`^(\d+ / \d+)+$` を対象にして刷り直せるようにする)。
2. **バグ1(根本+保険の二段構え)**:
   - 根本: FINALIZE冒頭で「FINALIZE適用済みマーカー」(デッキ内の不可視メタ=スライドの
     description等)を確認し、適用済みなら書き込みをスキップ(再実行を無害化)。
     併せてトリガー一覧を確認し、生成系トリガーを1本に統一
     (V99とV116が併存していれば片方削除)。
   - 保険: V88末尾の重複もみ消しを強化——ページ番号箱(`^(\d+ / \d+){2,}$`→正規化)、
     任意テキストの`X+X→X`正規化、スタンプ重複削除——をPDF工程直前に移す
     (多重実行に巻き込まれない位置で最後に1回だけ掃除する)。
3. **バグ2**: まずDBの`散水場所説明2〜4`を目視確認。データ起因ならAppSheet側の入力の問題で
   コード修正不要。コード起因の痕跡は無し。
4. 修正後、テスト案件で再生成し、二重が消えたこと・他項目が壊れていないことを確認。

### 留意(ハッキリ言っておくべきこと)
- このプロジェクトは同名関数の多重定義・同一ファイル内のコード重複
  (例: 報告書追加写真_V96恒久.gs に同じブロックが3回、V114に2回)が積み重なっており、
  **どのパッチが本当に効いているかがファイルの読み込み順に依存する**危険な状態。
  今回は最小修正に留めるが、いずれ「効いているコードだけを1本に整理する」ことを強く推奨する。
- GASへの反映はApps Scriptエディタへの貼り付け(またはclasp push)が必要。
  このリポジトリのバックアップを書き換えても本番GASには反映されない。
